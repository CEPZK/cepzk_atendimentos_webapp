# Supabase project setup checklist

One-time, in this order. The web app cannot boot without step 1–3, and sign-in cannot work without
step 4–6.

1. **Create the project** — pick the region closest to users (`sa-east-1` São Paulo for this product;
   latency to the DB dominates this app and there is no CDN in front of Postgres). Note the project ref.
2. **Record keys** — Project Settings → API Keys: publishable key (+ its name), and keep the service
   role key out of this repo entirely.
3. **`supabase link --project-ref <ref>`** in the backend repo; commit `supabase/config.toml` with the
   project id and `disabled` migrations list. Do not commit `supabase/.temp/`.
4. **Auth → Providers → Email**: enable "Magic link"/OTP. Add a custom SMTP sender **before** any real
   user is invited — Supabase's built-in sender is capped at ~2 messages/hour for testing and silently
   drops the rest, which shows up as "the sign-in button does nothing".
   Recommended SPF/DKIM/DMARC on the sending domain or half your links land in spam.
5. **Auth → URL Configuration**: Site URL = production origin; Redirect URLs += the three entries in
   `auth.md` §2.
6. **Auth → Rate Limits / Session**: OTP expiry ≤ 15 min; "Create new users" disabled if you want
   invite-only (mirrors `NEXT_PUBLIC_ALLOW_SELF_SIGNUP=false` — the app flag alone is not the boundary,
   this one is).
7. **Database → Roles**: confirm `anon` has **no** `GRANT` on `public` beyond what RLS should govern;
   revoke `truncate` from non-admin roles.
8. **Migrations**: apply `contracts/sql/0001_identity.sql` as `supabase/migrations/<ts>_identity.sql`
   verbatim (filename prefix from `supabase migration new`), then `0002_domain` once specified. Pin the
   contract hash in your migration header: `-- contract: sha256/…`, copied from
   `contracts/CONTRACT.sha256` (regenerated by `npm run contract:hash -- --write`). A hash file can never
   contain its own digest, which is why the value lives beside the SQL, not inside it.
9. **`npm run types:generate`** in the web repo with `SUPABASE_PROJECT_REF=<ref>` — must print
   `✓ no table-level drift`.
10. **Branching**: enable Supabase Branching once the preview-vs-prod split matters; every Vercel preview
    pointing at the production database is how a UI experiment becomes a data migration. Until then, do
    not run destructive client-side code against prod.
11. **Backups + PITR**: decide before any real atendimento is stored. Point-in-time recovery is a paid
    tier; a nightly `pg_dump` to object storage is not, and is the fallback for either.

## Non-obvious gotchas already handled by this repo

| Symptom                                         | Cause                                             | Where it is fixed                            |
| ----------------------------------------------- | ------------------------------------------------- | -------------------------------------------- |
| Signed in as the wrong user on a preview URL    | response cached with another user's `Set-Cookie`  | `dynamic = "force-dynamic"` on auth surfaces |
| Infinite redirect after sign-in                 | `/auth/callback` excluded from the proxy matcher  | `src/proxy.ts` matcher comment               |
| Random logouts ~1h in                           | refresh ran in an RSC that cannot write cookies   | `src/lib/supabase/proxy.ts`                  |
| Magic link opens production, not the PR preview | `emailRedirectTo` built from a build-time env var | `requestOrigin(headers())` in actions        |
| Session survives "disable user"                 | only sign-in was blocked                          | `is_active_member()` in every policy         |
